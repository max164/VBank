# VBank — технологический стек

## 1. Назначение документа

Документ фиксирует целевой технологический стек VBank после отказа от Java-реализации в пользу серверной части на Python, отдельного веб-приложения и консольного клиента.

Документ задаёт технические решения верхнего уровня. Подробные зависимости и версии фиксируются при создании проекта в `pyproject.toml` и `frontend/package.json`.

## 2. Общая схема

VBank строится как система из четырёх частей:

* серверная часть — Python-приложение с HTTP API;
* веб-приложение — отдельное приложение на TypeScript;
* консольный клиент — внешний клиент API для разработки и проверки;
* база данных — PostgreSQL.

Единый договор между клиентами и сервером — API с базовым путём `/api/v1`.

## 3. Серверная часть

### 3.1. Основной стек

* Python — язык серверной части и консольного клиента;
* FastAPI — HTTP API;
* Pydantic — проверка входных и выходных моделей;
* SQLAlchemy — работа с PostgreSQL и транзакциями;
* Alembic — миграции БД;
* psycopg — драйвер PostgreSQL;
* Typer — консольный клиент;
* pytest — тесты.

Первая версия серверной части использует синхронную работу с БД. Асинхронный доступ к БД не вводится без отдельного решения.

### 3.2. Безопасность

* argon2-cffi — хэширование паролей;
* PyJWT — выпуск и проверка `access token`;
* `refresh_session` в PostgreSQL — хранение отзывных refresh-сессий;
* CORS-настройки FastAPI — доступ веб-приложения к API;
* проверка ролей на серверной стороне.

Для веб-приложения `refresh token` СЛЕДУЕТ хранить в cookie с признаками `HttpOnly`, `Secure`, `SameSite`.

Для консольного клиента `refresh token` СЛЕДУЕТ хранить в пользовательском хранилище вне репозитория.

### 3.3. Наблюдаемость

* structlog — структурированные логи;
* `request_id` — сквозной идентификатор HTTP-запроса;
* журнал аудита — предметная история значимых действий.

## 4. Веб-приложение

### 4.1. Основной стек

* React — построение интерфейса;
* TypeScript — типизация клиентского кода;
* Vite — сборка и локальная разработка;
* MUI — библиотека компонентов интерфейса;
* React Router — маршрутизация;
* TanStack Query — запросы к API и состояние серверных данных;
* React Hook Form — формы;
* Zod — проверка данных форм на стороне интерфейса.

MUI выбран как базовая библиотека интерфейса, потому что VBank требует много форм, таблиц, фильтров, статусов и рабочих мест по ролям.

### 4.2. Границы ответственности

Веб-приложение отвечает за удобство работы пользователя, навигацию, формы, таблицы и отображение ошибок.

Веб-приложение не является источником предметных правил. Проверки интерфейса допустимы для быстрого ответа пользователю, но окончательные ограничения проверяет серверная часть.

## 5. Консольный клиент

Консольный клиент является первым внешним интерфейсом VBank.

Он используется для:

* проверки API до готовности веб-приложения;
* прохождения основных сценариев;
* подготовки демонстрационных данных;
* диагностики ошибок интеграции.

Консольный клиент работает через HTTP API и не импортирует прикладной слой серверной части.

## 6. API

Базовый путь API остаётся `/api/v1`.

API СЛЕДУЕТ проектировать как устойчивый договор для двух внешних клиентов:

* веб-приложения;
* консольного клиента.

Основные правила API:

* единый формат ошибок `{code, message, details, request_id}`;
* `request_id` обозначает HTTP-запрос, а заявка во внешнем API обозначается `application_id`;
* идемпотентность изменяющих запросов через `Idempotency-Key`;
* проверка доступа по ролям;
* пагинация списков;
* явные команды для предметных действий: одобрение заявки, отклонение заявки, закрытие счёта, компенсация операции.

## 7. Тестирование

Минимальный набор проверок:

* модульные тесты доменных правил;
* интеграционные тесты PostgreSQL;
* тесты API через HTTP-клиент;
* тесты идемпотентности изменяющих запросов;
* тесты консольного клиента как внешнего клиента API.

Для сценариев с БД СЛЕДУЕТ использовать реальный PostgreSQL в тестовом окружении, а не заменять его полностью имитацией.

## 8. Решения, не входящие в первую версию

В первую версию не входят:

* асинхронная работа с БД;
* отдельная система разрешений помимо ролей `Client`, `Operator`, `Admin`;
* настольное клиентское приложение;
* прямой доступ консольного клиента к прикладному слою серверной части;
* микросервисное разделение.
