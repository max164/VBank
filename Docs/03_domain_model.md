# VBank — доменная модель

## 1. Контексты

### 1.1. `auth`

Отвечает за регистрацию, вход, обновление сессии и выход.

### 1.2. `user`

Отвечает за жизненный цикл пользователя, его статус и роль.

### 1.3. `account`

Отвечает за открытие, состояние и баланс счёта.

### 1.4. `transaction`

Отвечает за выполнение финансовых операций и создание проводок.

### 1.5. `request`

Отвечает за ручное рассмотрение действий, которые не выполняются напрямую.

### 1.6. `dictionary`

Отвечает за управляемые справочники.

### 1.7. `setting`

Отвечает за режимы работы системы.

### 1.8. `audit`

Отвечает за неизменяемый журнал действий.

## 2. Агрегаты и сущности

### 2.1. `User`

**Назначение:** субъект системы.

**Ключевые атрибуты:**

* `user_id`
* `email`
* `username`
* `phone_number`
* `password_hash`
* `role`
* `status`
* `registered_at`

**Инварианты:**

* `email`, `username`, `phone_number` уникальны;
* пользователь со статусом `Blocked` не может входить и инициировать новые действия;
* у пользователя в каждый момент времени ровно одна активная роль.

### 2.2. `Account`

**Назначение:** хранение денежных средств пользователя.

**Ключевые атрибуты:**

* `account_id`
* `account_number`
* `user_id`
* `currency_id`
* `account_type_code`
* `balance`
* `negative_balance_limit`
* `status`
* `created_at`
* `closed_at`

**Инварианты:**

* уникальность `(user_id, currency_id, account_type_code)`;
* `account_number` уникален в системе;
* заблокированный счёт видим в списках и истории, но не участвует в новых операциях и не закрывается;
* закрытый счёт не участвует в новых операциях;
* `negative_balance_limit` допустим только для типа счёта с `allow_negative_balance = true`.

### 2.3. `Transaction`

**Назначение:** бизнес-факт изменения денежных средств.

**Ключевые атрибуты:**

* `transaction_id`
* `transaction_type`
* `from_account_id`
* `to_account_id`
* `amount`
* `currency_id`
* `status`
* `reason_code`
* `initiator_user_id`
* `related_transaction_id`
* `created_at`
* `completed_at`

**Инварианты:**

* `amount > 0`;
* `Transfer` не может быть направлен на тот же счёт;
* `Withdraw` не допускает отрицательный итоговый баланс;
* при `Success` создаются согласованные проводки;
* `Compensation` ссылается на исходную операцию.

### 2.4. `Request`

**Назначение:** ручное рассмотрение действий.

**Ключевые атрибуты:**

* `request_id`
* `request_type`
* `status`
* `initiator_user_id`
* `operator_user_id`
* `payload`
* `reason_code`
* `result_entity_type`
* `result_entity_id`
* `created_at`
* `decided_at`

**Инварианты:**

* во внешнем API идентификатор заявки называется `application_id`, чтобы не смешиваться со сквозным `request_id` HTTP-запроса;
* заявка создаётся только для сценария, переведённого в ручной режим;
* `Approved` и `Rejected` являются финальными состояниями;
* одобрение создаёт результат предметной области;
* `payload` валидируется по `request_type`.

### 2.5. Справочные сущности

* `Currency`
* `AccountType`
* `ReasonCode`
* `SystemSetting`

Справочные сущности участвуют в валидации доменных правил, но не содержат самостоятельных денежных сценариев.

### 2.6. `LedgerEntry`

Проводка не является самостоятельным бизнес-процессом. Она создаётся только как следствие успешной финансовой операции.

Сумма проводки хранится со знаком: отрицательное значение означает списание со счёта, положительное значение означает зачисление на счёт.

### 2.7. `AuditLog`

Запись аудита фиксирует попытку и результат действия, но не меняет доменное состояние.

## 3. Доменные правила

### 3.1. Правила денег

* рабочим состоянием счёта является `balance`;
* `LedgerEntry` используется для аудита, сверки и восстановления;
* сумма проводки хранит направление движения денег через знак;
* валюты затронутых счетов и операции должны совпадать;
* операция выполняется атомарно.

### 3.2. Правила отрицательного баланса

* минус допускается только для `Transfer`;
* тип счёта должен разрешать отрицательный баланс;
* счёт должен иметь `negative_balance_limit`;
* итоговый баланс должен удовлетворять правилу `balance_after >= -negative_balance_limit`.

### 3.3. Правила заявок

* `UserRegistration` и `AccountOpening` идут через `Request` только при ручном режиме;
* `Deposit` и `Withdraw` всегда идут через `Request`;
* `Transfer` идёт через `Request` только при `internal_transfer_mode = manual`;
* внешний запрос перевода использует `to_account_number`, а серверная часть определяет связанный `to_account_id`;
* при `Rejected` результат предметной области не создаётся.

### 3.4. Правила доступа

* `Client` работает только со своими объектами;
* `Operator` управляет заявками, статусами пользователей и служебными действиями;
* `Admin` управляет справочниками, режимами работы системы и аудитом.

## 4. Состояния

### 4.1. `User.status`

* `Active -> Blocked`
* `Blocked -> Active`

### 4.2. `Account.status`

* `Active -> Blocked`
* `Blocked -> Active`
* `Active -> Closed`

### 4.3. `Request.status`

* `PendingApproval -> Approved`
* `PendingApproval -> Rejected`

### 4.4. `Transaction.status`

* `Success`
* `Rejected`
