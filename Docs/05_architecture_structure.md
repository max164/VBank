# VBank — архитектура и структура проекта

## 1. Архитектурный обзор

VBank состоит из четырёх основных частей:

* `backend` — серверное Python-приложение с HTTP API и прикладной логикой;
* `frontend` — отдельное веб-приложение для ролей `Client`, `Operator`, `Admin`;
* `cli` — консольный внешний клиент для разработки, проверки и приёмки сценариев;
* `database` — PostgreSQL.

Единым договором между клиентами и серверной частью является API с базовым путём `/api/v1`.

### Назначение слоёв

* `api` — маршруты HTTP API, входные и выходные модели, преобразование ошибок;
* `application` — прикладные сценарии, границы транзакций и координация репозиториев;
* `domain` — сущности, значения, инварианты и интерфейсы репозиториев;
* `infrastructure` — работа с БД, безопасность, конфигурация и интеграция с используемыми библиотеками.

### Правило для `shared`

В `shared` допускаются только общие технические элементы: подключение к БД, конфигурация, базовые ошибки, безопасность, общий формат ответа, `request_id`, журналирование и вспомогательные типы.

Доменные правила конкретных контекстов не выносятся в `shared`.

```text

├── transaction.py
├── request.py
├── user.py
├── dictionary.py
├── setting.py
└── audit.py
```

Консольный клиент работает только через `/api/v1`.

Консольному клиенту ЗАПРЕЩЕНО импортировать прикладной или доменный слой серверной части. Это сохраняет API единственным договором между сервером и внешними клиентами.

```text
frontend/
├── src/
│   ├── app/

│   ├── auth/
│   ├── layouts/

│   └── shared/
├── package.json
├── vite.config.ts
└── tsconfig.json
```

Веб-приложение является отдельным клиентом API.

Веб-приложение отвечает за:

* маршрутизацию экранов;
* формы и таблицы;
* хранение состояния интерфейса;
* отображение ошибок API;
* разделение рабочих областей по ролям.

Веб-приложению ЗАПРЕЩЕНО дублировать доменные инварианты как источник истины. Проверки в интерфейсе допустимы только для удобства пользователя; окончательное решение принимает серверная часть.

## 6. Архитектурные правила

### 6.1. Модульность

* верхний уровень серверной части делится по контекстам предметной области, а не по ролям пользователей;
* роли `Client`, `Operator`, `Admin` управляют доступом, но не образуют отдельные серверные модули;
* веб-приложение может иметь отдельные страницы по ролям, но они используют общий API.

### 6.2. Транзакции

* денежные сценарии завершаются в слое `application`;
* работа с балансом и проводками выполняется в одной транзакции БД;
* конкурентный доступ к затрагиваемым счетам контролируется блокировкой строк;
* первая версия серверной части использует синхронную работу с БД.

### 6.3. API

* базовый путь API — `/api/v1`;
* API используется и веб-приложением, и консольным клиентом;
* изменяющие запросы принимают `Idempotency-Key`;
* ошибки возвращаются в едином формате `{code, message, details, request_id}`;
* `request_id` в API означает сквозной идентификатор HTTP-запроса;
* заявки во внешнем API используют `application_id`;
* правила доступа проверяются на серверной стороне.

### 6.4. Источник правил

* предметные правила задаются в `03_domain_model.md`;
* физическая схема хранения задаётся в `04_data_model.md`;
* целевой стек задаётся в `09_technology_stack.md`;
* архитектурный документ не дублирует доменные и табличные правила.

## 7. Ресурсы и миграции

```text
migrations/
├── env.py
├── script.py.mako
└── versions/
```

### Правила

* миграции выполняются через Alembic;
* миграции только вперёд;
* начальные справочники и режимы работы системы должны быть воспроизводимы;
* секреты не хранятся в репозитории.
